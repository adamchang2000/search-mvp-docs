---
title: "Source disagreements"
description: "When sources disagree about a fact, tell us which one you went with, and why."
---

Agents constantly resolve conflicts between sources, usually without saying so. A disagreement record
captures that judgment: which sources disagreed about a fact, which one the agent went with, and why it set
the others aside. It's the [first kind of feedback](/feedback/overview) search-mvp takes, and it tells the
search engine which sources to trust, and when.

## An example

A user asks where to go for a romantic dinner in San Francisco, about $150 for two. The agent searches, and two
well-known guides both list Trestle's prix fixe at **$45**: Time Out's romantic-restaurants list and Eater
SF's map. Then it opens Trestle's own menu, which says **$52** for four courses.

The agent goes with the menu. The guides aren't wrong so much as out of date: Time Out's piece is from
February 2025, and Eater's map from 2022, several price rises ago. It answers $52, and records why:

```json
{
  "fact": "Trestle's prix fixe price per person",
  "went_with": {
    "web_query_id": "771302518",
    "url": "https://www.trestlesf.com/menu",
    "says": "$52 per person for the four-course prix fixe",
    "why": "The restaurant's own current menu."
  },
  "set_aside": [
    {
      "web_query_id": "464394922",
      "url": "https://www.timeout.com/san-francisco/restaurants/romantic-restaurants-in-san-francisco",
      "says": "Weekly $45 prix-fixe menu",
      "reason": "stale",
      "why": "Published February 2025, before the price rose to $52."
    },
    {
      "web_query_id": "464394922",
      "url": "https://sf.eater.com/maps/most-romantic-restaurants-san-francisco",
      "says": "Prix fixe costs just $45",
      "reason": "stale",
      "why": "Published 2022, several price increases ago."
    }
  ],
  "prompted_by_user": false
}
```

The menu was a page the agent read with fetch `771302518`, so it's cited by that fetch's `web_query_id`.
The guides came from search `464394922`, and are cited by its `web_query_id`.

Without the record, the next agent that asks a similar question meets the same two guides, near the top
of its results, saying the same out-of-date $45. Either it spends extra searches and fetches tracking down
the menu to check, or it quotes $45 and the user finds out at the table.

With records like this one, the search engine learns that those guides have gone stale on this fact, and
where the current price lives. Once feedback is served, a later search that returns those guides will also
return Trestle's menu, right beside them. That's meant to pay off twice:

- **Lower search costs.** The agent doesn't need more searches to double-check the price: the current one
  is already in its results.
- **Fewer frustrated users.** The agent doesn't quote the stale $45.

<Note>
This example comes from our own testing: agents asked this kind of question met Trestle's $45 listings
again and again, and the ones that checked recorded this disagreement.
</Note>

## When to record one

Record a disagreement whenever two or more sources say different things about a **fact that has one right
answer**, such as a price, opening hours, a date, a figure, a plan's limits, or whether a place is still open,
and you go with one of them. Record it:

- even when the difference is small;
- even when the agent settled it without mentioning it to the user;
- even when it isn't sure which source is right. We want the judgment call, not a verdict that a source is
  wrong.

Don't record differences of opinion or experience (whether a room is noisy, whether the food is good), or
figures that depend on who measured them and how (benchmarks, test results, ratings).

Record it as soon as the call is made, before replying. One record per disagreement.

## The record

| Field | |
|---|---|
| `fact` | What the sources disagree about, e.g. `"Trestle's prix fixe price"`. |
| `went_with` | The source you went with: `web_query_id`, `url`, what it `says`, and `why` you chose it. |
| `supported_by` | Other sources that agree with it, each with `web_query_id`, `url` and `says`. Optional. |
| `set_aside` | Every source you didn't go with (at least one): `web_query_id`, `url`, `says`, a `reason`, and `why`. |
| `prompted_by_user` | `true` if the user prompted it (e.g. questioned a fact); `false` if you noticed it yourself. |

`reason` is why a set-aside source differs, as best you can tell:

| reason | |
|---|---|
| `stale` | It was probably right when written, but something has changed since. |
| `biased` | It has a reason to shade it (an ad, a promotion, a competitor). |
| `incorrect` | It got it wrong. |
| `unclear` | You can't tell. |

The full schema is in the [API reference](/api-reference/feedback).

## Citing sources

Each source is identified by where you found it:

- **A search result:** the `web_query_id` of the search that returned it (the search response's `id`), and
  its URL as shown with the result.
- **A page you fetched:** the `web_query_id` of the fetch that read it (the fetch response's `id`), and the
  URL as you fetched it or as it was redirected to. The fetch must have returned the page.

The id resolves against your searches and fetches alike, and must resolve. Sources may still use the older
field names `search_query_id` and `fetch_id` (SDKs before 0.5.0, MCP clients with cached tool definitions):
they're deprecated, and read the same way as `web_query_id`. Records from clients that send no id (SDK before
0.2.0) are still accepted: a source without one resolves if you fetched its URL and got a page back.

Sources must come from your own searches and fetches of the last 7 days. URLs that differ only in form count as the
same page: `http` or `https`, `www.` or not, a trailing slash, a `#fragment`, or tracking parameters like `utm_*`.
A URL with part of its query string or path dropped (`/products/refill` for `/products/refill?variant=4355`)
also counts, as long as it matches only one result of the cited search, or the cited fetch's page. Send the URL as
shown with the result when you can.

## Invalid records

Every record is stored, even an invalid one. One that doesn't match the schema, or cites a source we can't
find among your searches' results and fetched pages, gets a `422 invalid_record` whose `details.errors` lists
each problem with a JSON pointer into the record:

```json
{
  "error": "unprocessable",
  "code": "invalid_record",
  "message": "the record doesn't match the source_disagreement schema, or a source doesn't resolve (it was stored)",
  "retryable": false,
  "details": { "errors": [{ "path": "/set_aside/0/url", "message": "not among the results of search 464394922" }] },
  "request_id": "req_…"
}
```

The whole record is invalid if any part is: a record's meaning depends on all of its sources.
